<p>The central communication rule is the same as in <a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/rapm/" class="wiki-link">RAPM</a>: measured and projected pages must remain visually and linguistically distinct. A daily curve records what the model estimated from evidence available by a date. An orange trajectory or 2026-27 win distribution is a forecast built on top of that curve.</p>
<h2 id="generated-not-authored-in-place">Generated, not authored in place</h2>
<p>The public repository is downstream of <code>unified-rapm</code>. Exporters write player series, tables, team data, projections, accuracy, and API files; the build copies the site shell and clears stale output. Andrew then reviews the staged diff and decides whether to commit and push.</p>
<p>This arrangement has two benefits:</p>
<ul>
<li>public data can be reproduced from the model artifacts rather than manually edited;</li>
<li>owner review remains a publication gate for claims, large diffs, and accidental private material.</li>
</ul>
<p>It also creates a sharp hazard: a hand edit in <code>andrewjparkus.github.io</code> will be overwritten by the next build. The durable fix for a page belongs in the corresponding source template or exporter recorded in <a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/daily-rapm-implementation-map/" class="wiki-link">Daily RAPM implementation map</a>.</p>
<h2 id="public-explanation-versus-executable-truth">Public explanation versus executable truth</h2>
<p>The site is unusually candid about weaknesses: external EPM beats the internal decomposition on the frozen preseason benchmark; game evaluation uses realized minutes; non-overlapping forward correlation is far below the overlap-inflated headline; cross-league jumps are weakly identified; and player standard errors approximate rather than fully invert the ridge geometry.</p>
<p>That honesty must include documentation drift. At the inspected build, <code>model.html</code> says projected net is never modeled directly. The current forward code and <code>projection_2026_27.json</code> instead identify the production model as <strong>“xgboost (single-net aggregate re-decomposed to sum6) + aging fallback.”</strong> The public arithmetic remains coherent because the aggregate forecast is redistributed into the six factors, but the method prose should be refreshed. This is a documentation mismatch, not a reason to erase the more recent implementation from Rome.</p>
<p>There are similar reasons to prefer artifact-backed prose:</p>
<ul>
<li>a simulation count can change;</li>
<li>a minutes contract can be promoted or reverted;</li>
<li>an ablation can leave some feature cells dormant;</li>
<li>a ledger can refuse to render after a reproducibility drift;</li>
<li>a generated page can lag a source-code correction.</li>
</ul>
<p>A future model manifest should let each prose claim point to the exact build contract it describes.</p>
<h2 id="relationship-to-rome">Relationship to Rome</h2>
<p>Rome should retain the conceptual map and durable lessons:</p>
<ul>
<li><a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/rapm-lineup-model/" class="wiki-link">RAPM lineup model</a> for the estimator;</li>
<li><a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/six-factor-rapm-decomposition/" class="wiki-link">Six-factor RAPM decomposition</a> for interpretation;</li>
<li><a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/cross-league-rapm-translation/" class="wiki-link">Cross-league RAPM translation</a> for league comparison;</li>
<li><a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/nba-player-forward-projection-model/" class="wiki-link">NBA player forward projection model</a> and <a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/nba-team-season-projection-model/" class="wiki-link">NBA team season projection model</a> for forecasting;</li>
<li><a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/rapm-evaluation-and-uncertainty/" class="wiki-link">RAPM evaluation and uncertainty</a> for claims and caveats;</li>
<li><a href="/rome-wiki/articles/basketball/nba-multi-agent-forecasting-company/current-rapm-decomp-csv-export/" class="wiki-link">Current RAPM decomp CSV export</a> for a specific data delivery.</li>
</ul>
<p>The GitHub Pages repository remains the display artifact. Rome should not duplicate thousands of generated player JSON files or pretend a point-in-time ranking is evergreen knowledge. It should explain how to read the product, record important version changes, and connect the model to Andrew's broader <a href="/rome-wiki/wanted/nba-multi-agent-forecasting-company/" class="wiki-link wiki-link-missing" title="Unwritten article — a research thread waiting to be followed">NBA multi-agent forecasting company +</a>.</p>
<h2 id="open-questions">Open questions</h2>
<ul>
<li>How should the site display model-version and data-as-of information without cluttering every page?</li>
<li>Which public methodology claims can be generated directly from artifact metadata to prevent drift?</li>
<li>Should the static API expose uncertainty provenance and fallback flags as prominently as point estimates?</li>
<li>What privacy and licensing review is required before expanding the public data surface?</li>
