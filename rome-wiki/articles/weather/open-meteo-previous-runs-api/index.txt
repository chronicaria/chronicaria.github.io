1e:T2a49,<h2 id="the-endpoint-not-the-plain-forecast-api">The endpoint (NOT the plain Forecast API)</h2>
<p><code>https://previous-runs-api.open-meteo.com/v1/forecast</code> — a <strong>separate host</strong> from <code>api.open-meteo.com</code>. Same query grammar as the Forecast API, but this is the one that actually <em>serves</em> the <code>_previous_dayK</code> data.</p>
<aside class="callout callout-warning">
<p class="callout-title">Warning</p>
<p>The main Forecast API silently returns nulls
<code>api.open-meteo.com/v1/forecast</code> <strong>accepts</strong> <code>temperature_2m_previous_day1</code> (HTTP 200, no error) but returns an all-<code>null</code> column. You must use the <code>previous-runs-api</code> host to get real values. Live-verified 2026-07-06 — same request, main host = all null, previous-runs host = real numbers.</p>
</aside>
<p>Free, no API key, <strong>CORS <code>access-control-allow-origin: *</code></strong> (verified via live headers + OPTIONS preflight → <code>GET, POST, OPTIONS</code>). Callable straight from a browser.</p>
<h2 id="what-means-the-exact-semantics">What <code>_previous_dayK</code> means (the exact semantics)</h2>
<p>For a given valid hour <code>h</code>, <code>temperature_2m_previous_dayK</code> is <strong>the value that was forecast K days (24·K hours) before <code>h</code></strong> — i.e. a <strong>K-day-lead forecast</strong> for that hour. <code>day1</code> = predicted 24 h ahead, <code>day2</code> = 48 h ahead, … up to <code>day7</code> = 168 h ahead.</p>
<p>Subtlety (from Open-Meteo's own writeup): <code>previous_day1</code> is <em>not</em> a single model run from 24 h ago. It's a <strong>stitched series</strong> — for each hour, take the value from whichever run was initialised ~24 h earlier (they discard the first 24 h of each run, then the next 24 h, etc.). So each <code>_previous_dayK</code> column is a continuous time series where lead time is held constant. That's exactly what you want for skill-vs-lead analysis.</p>
<h2 id="range-and-coverage-live-verified">Range and coverage (live-verified)</h2>
<ul>
<li><strong>K = 1 … 7.</strong> <code>previous_day7</code> returns real data; <code>previous_day8</code>/<code>day9</code> are accepted syntactically (HTTP 200) but return <strong>all nulls</strong> — so <strong>7 is the true max lead</strong>.</li>
<li><strong>Base variables confirmed to support <code>_previous_dayK</code></strong>: <code>temperature_2m</code>, <code>precipitation</code>, <code>wind_speed_10m</code>, <code>relative_humidity_2m</code>, <code>apparent_temperature</code> — all returned real non-null data. (Docs also list dewpoint, pressure, cloud cover, wind direction, etc.; the suffix is general across the model's surface variables.)</li>
<li><strong><code>past_days</code> max = 93</strong> (server error: <em>"Allowed range 0 to 93"</em> — note it's <strong>93, not 92</strong>). Combine <code>&#x26;past_days=N</code> with the <code>_previous_dayK</code> columns to pull up to ~3 months of already-verifiable past hours in one call.</li>
<li>Archive depth: most models from ~Jan 2024; GFS 2 m temp back to Mar 2021.</li>
</ul>
<h2 id="the-phase-4-pattern-no-backend-no-snapshots">The Phase-4 pattern (no backend, no snapshots)</h2>
<p>For each past hour <code>h</code> in the response:</p>
<ul>
<li><strong>actual / truth proxy</strong> = <code>temperature_2m[h]</code> (the current best estimate — see truth note below)</li>
<li><strong>K-day-lead forecast</strong> = <code>temperature_2m_previous_dayK[h]</code></li>
<li><strong>error</strong> = <code>temperature_2m[h] − temperature_2m_previous_dayK[h]</code></li>
</ul>
<p>Aggregate over the last N days (up to 93) → MAE / bias per lead time K. This is the whole "how accurate were recent forecasts?" panel, computed client-side. You do <strong>not</strong> need to snapshot your own forecasts (the concern flagged in <a href="/rome-wiki/articles/weather/nyc-weather-dashboard/" class="wiki-link">NYC weather dashboard</a>'s "when you'd need a backend") — Open-Meteo already archived them.</p>

<p>For a past hour, the plain <code>temperature_2m</code> on both the Forecast API and this endpoint is a <strong>best-estimate analysis blend</strong> (the most-recent/best run's assimilated state), <strong>not</strong> raw observations. Live NYC check for 2026-07-01:</p>

<p>Monotonic and lands squarely on the <a href="/rome-wiki/articles/weather/temperature-forecast-confidence-intervals/" class="wiki-link">Temperature forecast confidence intervals</a> table (day1 ~3.0, day3 ~3.5, day5 ~4.5) and the task's sanity band (day1 2–3, day3 3–4, day5 4–5 °F). <strong>Use this as a built-in bug check</strong>: if your computed curve is flat, non-monotonic, or off by 10×, it's a wiring bug — almost always the wrong host (all-null columns), a column-misalignment, or a °C/°F mixup.
