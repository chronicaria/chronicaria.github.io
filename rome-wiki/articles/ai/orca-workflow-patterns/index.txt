1d:T1652,<h2 id="pattern-1-same-task-race">Pattern 1: same-task race</h2>
<p>Use this when the task has a clear endpoint and the quality of the diff is easy to compare.</p>
<p>Examples:</p>
<ul>
<li>Fix one reproducible bug.</li>
<li>Improve one slow query.</li>
<li>Refactor one component.</li>
<li>Repair one failing test.</li>
</ul>
<p>Run the same prompt in three worktrees, preferably with different agents. Compare:</p>
<ul>
<li>Did it reproduce or understand the bug?</li>
<li>Did the diff stay small?</li>
<li>Did it add or update tests?</li>
<li>Did checks pass?</li>
<li>Did it create new risk?</li>
</ul>
<p>This is the best beginner pattern because it teaches how each agent actually behaves.</p>
<h2 id="pattern-2-builder-and-reviewer">Pattern 2: builder and reviewer</h2>
<p>Use this when one promising implementation needs scrutiny before it deserves more work.</p>
<p>Flow:</p>
<ol>
<li>Builder agent implements the change.</li>
<li>Reviewer agent inspects only the diff and relevant files.</li>
<li>Human annotates the diff with the best review points.</li>
<li>Builder revises from one batched review prompt.</li>
<li>Human runs final checks and ships.</li>
</ol>
<p>This avoids the common failure mode where the same agent rationalizes its own change.</p>
<h2 id="pattern-3-specialist-split">Pattern 3: specialist split</h2>
<p>Use this when the task decomposes cleanly.</p>
<p>Examples:</p>
<ul>
<li>Agent A investigates the backend bug.</li>
<li>Agent B builds the frontend fix.</li>
<li>Agent C writes tests or migration notes.</li>
<li>Human merges only after all diffs are understood.</li>
</ul>
<p>This is better than a race when subtasks are truly independent. It is worse than a race when the split is artificial.</p>
<h2 id="pattern-4-red-team-pass">Pattern 4: red-team pass</h2>
<p>Use this after a good-looking change.</p>
<p>Prompt a fresh agent:</p>
<pre><code class="language-text">Review this worktree as a skeptical maintainer. Find correctness bugs, missing tests,
security issues, migration risks, and behavior changes. Do not edit yet. Report the
top issues with file paths and exact verification steps.
</code></pre>
<p>Then either ask the same agent to patch the issues in its own worktree or send the review back to the original builder through Orca's diff annotation loop.</p>
<h2 id="pattern-5-evidence-diverse-research">Pattern 5: evidence-diverse research</h2>
<p>Use this for research, planning, and technical design where independent evidence matters more than raw agent count.</p>
<p>Give agents different assignments:</p>
<ul>
<li>One searches official docs.</li>
<li>One reads the existing codebase.</li>
<li>One finds prior issues or commits.</li>
<li>One produces a synthesis and risk list.</li>
</ul>
<p>This mirrors <a href="/rome-wiki/articles/ai/designed-information-asymmetry-for-llm-forecasts/" class="wiki-link">Designed information asymmetry for LLM forecasts</a>: agents are more useful when they do not all see the same prompt and evidence.</p>
<h2 id="pattern-6-coordinator-and-workers">Pattern 6: coordinator and workers</h2>
<p>Use <a href="/rome-wiki/articles/ai/orca-inter-agent-orchestration/" class="wiki-link">Orca inter-agent orchestration</a> when there are dependencies, ownership, and completion states.</p>
<p>Good fits:</p>
<ul>
<li>"Audit these five modules and report <code>worker_done</code> when complete."</li>
<li>"Block on a decision gate if the API shape is ambiguous."</li>
<li>"Dispatch each worker a separate file family, then synthesize."</li>
</ul>
<p>Overkill fits:</p>
<ul>
<li>One quick bug fix.</li>
<li>A single review comment.</li>
<li>Anything where one terminal prompt is enough.</li>
</ul>
<h2 id="pattern-7-usage-and-rate-limit-routing">Pattern 7: usage and rate-limit routing</h2>
<p>Use Orca's account and usage visibility as a practical scheduler.</p>
<ul>
<li>Start with the agent most likely to solve the task.</li>
<li>When it approaches rate limits, move scout work, tests, or review to another agent.</li>
<li>Avoid spending top-tier usage on chores that a cheaper or less constrained agent can handle.</li>
<li>Keep the hard merge decision with the human.</li>
</ul>
<h2 id="prompt-kernels">Prompt kernels</h2>
<p>Builder:</p>
<pre><code class="language-text">Implement the smallest correct fix. Follow existing patterns. Run relevant checks.
Stop with files changed, checks run, and remaining risk. Do not commit or push.
</code></pre>
<p>Reviewer:</p>
<pre><code class="language-text">Review this diff as a maintainer. Prioritize correctness bugs, regressions,
missing tests, security issues, and maintainability risks. Do not rewrite style
unless it affects behavior. Give file-specific findings.
</code></pre>
<p>Research worker:</p>
<pre><code class="language-text">Investigate only your assigned slice. Cite sources or file paths. Do not solve
the whole problem. Return facts, uncertainties, and recommended next checks.
</code></pre>
<h2 id="anti-patterns">Anti-patterns</h2>
<ul>
<li>Many agents editing the same checkout.</li>
<li>Many agents receiving the same vague prompt with no testable endpoint.</li>
<li>Letting agents merge each other's work without human diff review.</li>
<li>Treating worktree isolation as a security boundary.</li>
<li>Keeping every attempt alive after the decision is made.</li>
<li>Using orchestration when a plain follow-up prompt is enough.</li>
</ul>
