17:T2455,<h2 id="repository-boundary">Repository boundary</h2>
<p>Two repositories play different roles:</p>
<ul>
<li><strong><code>unified-rapm</code></strong> is the research and build source of truth. It contains the solver drivers, priors, translation, forward models, validation harnesses, exporters, and private/generated artifacts.</li>
<li><strong><code>andrewjparkus.github.io</code></strong> is the generated public product. Its HTML, JavaScript, CSS, player data, projections, and API files are staged by the source build and then manually reviewed and published by Andrew.</li>
</ul>
<p>The public checkout should not be edited by hand: <code>build_pages.py</code> clears everything except its <code>.git</code> directory before restaging the site. Manual changes there are disposable by design. <a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/daily-rapm-public-site/" class="wiki-link">Daily RAPM public site</a> describes the user-facing surfaces.</p>

<h2 id="measurement-path">Measurement path</h2>
<p>The expensive substrate is the possession solve. The NBA driver builds or loads a large sparse matrix for each underlying component, slices it to a game-day's trailing five-year window, applies the 550-day decay, and solves the weighted ridge. NCAA and G League are solved on their native scales in separate processes.</p>
<p>The daily boards remain modular:</p>
<ul>
<li><code>out/nba</code> holds the pure NBA path;</li>
<li><code>out/nba_hybrid</code> holds whichever promoted prior-informed build produced it;</li>
<li><code>out/college</code> and <code>out/gleague</code> hold native feeder-league paths;</li>
<li>the aggregation stage applies canonical translation and writes the unified series.</li>
</ul>
<p>The unified parquet is several gigabytes and tens of millions of rows. Consumers should project columns and stream row groups rather than load it wholesale. This operational fact shapes the exporters and is part of why the public site contains compact downsampled JSON rather than the research corpus itself.</p>
<h2 id="projection-path">Projection path</h2>
<p>The forward stack deliberately starts after the descriptive measurement stack:</p>
<ol>
<li><code>oos_harness.py</code> extracts season-end causal snapshots.</li>
<li><code>build_forward_xgb.py</code> constructs temporal panels and trains factor/horizon plus aggregate-net models.</li>
<li><code>build_projection.py</code> applies gate decisions, fallbacks, exact re-decomposition, and calibrated intervals.</li>
<li>minutes, expected games, and roster inputs are built independently.</li>
<li><code>project_2027.py</code> combines the pieces into team strength and Monte Carlo outcomes.</li>
</ol>
<p>This separation makes “measured” and “projected” inspectable. A forecast model can be replaced without rewriting the historical RAPM curve, and a minutes-model experiment need not alter a player's per-100 rating.</p>
<h2 id="product-build-and-publication">Product build and publication</h2>
<p><code>deploy_site.sh</code> is the executable product definition. It rebuilds forward artifacts, runs exporters, invokes the site assembly clear step, reruns exporters that write directly into the fresh public checkout, and verifies required files exist. It stages but does not authorize publication. Andrew's review, commit, and push of the GitHub Pages repository are the final gate.</p>
<p>The source repository itself is local-only in the inspected configuration. Its ignored multi-gigabyte data is not protected by the public site's Git history. Source code, generated data, and published product therefore have different recovery and provenance contracts.</p>
<h2 id="which-files-answer-which-question">Which files answer which question</h2>
<ul>
<li>“What is the current mathematical model?” — <code>msolve.py</code>, <code>joint_alpha.py</code>, and the active calibration JSON.</li>
<li>“What actually ships?” — <code>deploy_site.sh</code> and the public artifact metadata.</li>
<li>“How was a model cell promoted?” — <code>forward_model_gate.json</code>, ablation artifacts, and <a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/rapm-evaluation-and-uncertainty/" class="wiki-link">RAPM evaluation and uncertainty</a>.</li>
<li>“Why does a feeder-league rating look compressed?” — <code>var_translate_v5.json</code> and <a href="/rome-wiki/articles/basketball/nba-quantitative-modeling/cross-league-rapm-translation/" class="wiki-link">Cross-league RAPM translation</a>.</li>
<li>“Why does the prose disagree with an artifact?” — inspect file dates and treat live code plus generated metadata as current until the documentation is refreshed.</li>
</ul>
<h2 id="open-questions">Open questions</h2>
<ul>
<li>Should a machine-readable model manifest version every solve regime, translation map, forward gate, minutes contract, and public build together?</li>
<li>Which large artifacts are irreplaceable and need an explicit backup plan outside Git?</li>
<li>Can the daily build become incremental without weakening causal and reproducibility gates?</li>
<li>How should generated public prose be tested against executable invariants such as the current net projection path?</li>
