<h2 id="the-data-see-weather-forecast-apis-">The data (see <a href="/rome-wiki/articles/weather/weather-forecast-apis/" class="wiki-link">Weather forecast APIs</a>)</h2>
<ul>
<li><strong>Bands + honest PoP</strong> → Open-Meteo <strong>Ensemble API</strong> (<code>ensemble-api.open-meteo.com/v1/ensemble</code>), which returns every member's hourly series. Free, no key, CORS-enabled, ~16-day horizon.</li>
<li><strong>Official line + alerts</strong> (optional) → <code>api.weather.gov</code> (deterministic, US-only).</li>
<li>NYC = <code>latitude=40.71&#x26;longitude=-74.01</code>. Use <strong>global</strong> models only: <code>gfs_seamless,ecmwf_ifs025,icon_seamless</code> (~119 members combined).</li>
</ul>
<p>Example request:</p>
<pre><code>https://ensemble-api.open-meteo.com/v1/ensemble
  ?latitude=40.71&#x26;longitude=-74.01
  &#x26;hourly=temperature_2m,precipitation,wind_speed_10m
  &#x26;models=gfs_seamless,ecmwf_ifs025,icon_seamless
  &#x26;forecast_days=16&#x26;temperature_unit=fahrenheit
  &#x26;wind_speed_unit=mph&#x26;precipitation_unit=inch
  &#x26;timezone=America%2FNew_York
</code></pre>
<h2 id="the-idea-in-one-line">The idea in one line</h2>
<p>Each ensemble member is one equally-likely future. For each hour, take <strong>percentiles across members</strong> → median line + shaded band; the band <strong>widens on its own</strong> with lead time because members diverge (do <em>not</em> hand-widen it — that double-counts uncertainty). Honest PoP = <strong>fraction of members that show rain</strong>. This directly connects to <a href="/rome-wiki/articles/weather/temperature-forecast-confidence-intervals/" class="wiki-link">Temperature forecast confidence intervals</a> — except here the band is <em>flow-dependent</em> (tight on calm days, wide before a front) instead of a fixed ±8 °F.</p>
<aside class="callout callout-warning">
<p class="callout-title">Warning</p>
<p>Small-sample percentiles
With only ~31–51 members, <code>p2.5/p97.5</code> (a nominal 95% band) jitter hour-to-hour because they ride a single order statistic. Draw <strong>p10/p90</strong> (label it "80% of members") for a steady envelope; optionally overlay faint min/max as "full spread."</p>
</aside>
<h2 id="core-compute-vanilla-js-runs-in-a-browser">Core compute (vanilla JS, runs in a browser)</h2>
<pre><code class="language-js">const LAT = 40.71, LON = -74.01, PRECIP = 0.01; // inch threshold
const url = `https://ensemble-api.open-meteo.com/v1/ensemble`
  + `?latitude=${LAT}&#x26;longitude=${LON}`
  + `&#x26;hourly=temperature_2m,apparent_temperature,precipitation,wind_speed_10m`
  + `&#x26;models=gfs_seamless,ecmwf_ifs025,icon_seamless`
  + `&#x26;forecast_days=16&#x26;temperature_unit=fahrenheit`
  + `&#x26;precipitation_unit=inch&#x26;wind_speed_unit=mph&#x26;timezone=America%2FNew_York`;

// gather every member array for a variable → [ [members@h0], [members@h1], ... ]
const membersOf = (hourly, v) => {
  const keys = Object.keys(hourly).filter(k => k.startsWith(v + '_member'));
  const H = hourly.time.length;
  return Array.from({length: H}, (_, h) =>
    keys.map(k => hourly[k][h]).filter(x => x != null));
};
const pct = (vals, p) => {                 // linear-interpolated percentile
  if (!vals.length) return null;
  const s = [...vals].sort((a,b) => a-b);
  const i = (p/100) * (s.length-1), lo = Math.floor(i), hi = Math.ceil(i);
  return lo === hi ? s[lo] : s[lo] + (s[hi]-s[lo])*(i-lo);
};

const { hourly } = await (await fetch(url)).json();
const T = membersOf(hourly,'temperature_2m');
const A = membersOf(hourly,'apparent_temperature'); // Steadman feels-like, per member
const P = membersOf(hourly,'precipitation');
const W = membersOf(hourly,'wind_speed_10m');

const series = hourly.time.map((t,h) => ({
  time: t,
  tMed: pct(T[h],50), tLo: pct(T[h],10), tHi: pct(T[h],90), // widening band
  feelsMed: pct(A[h],50), feelsLo: pct(A[h],10), feelsHi: pct(A[h],90),
  pop: P[h].length ? P[h].filter(v => v > PRECIP).length / P[h].length : null,
  wind: pct(W[h],50),
}));
</code></pre>
<p>Feed <code>series.map(s=>s.tLo)</code> / <code>tHi</code> as the two band edges and <code>tMed</code> as the center line. <code>apparent_temperature</code> (<a href="/rome-wiki/articles/weather/feels-like-temperature/" class="wiki-link">Steadman feels-like</a>) is per-member too, so it gets its own widening band for free.</p>

<h2 id="neighborhood-resolution--the-honest-limit">Neighborhood resolution — the honest limit</h2>
<p>The forecast is for <strong>"NYC generally," not your block.</strong> The <a href="/rome-wiki/articles/weather/urban-heat-island/" class="wiki-link">Urban heat island</a> is real (~2–8 °F between neighborhoods), but the models <strong>can't see it</strong>: a global-model grid cell (~9–25 km) is <em>bigger than Manhattan is wide</em> (~3.7 km), so Central Park and the South Bronx get essentially the same forecast. Verified live — two NYC points differed by only 0.1–0.8 °F, and even that tracks Open-Meteo's 90 m elevation correction, <strong>not</strong> any UHI physics (it models none).</p>
<p>Options, laziest first:</p>
<ul>
<li><strong>(A) Just be honest.</strong> Label it "NYC (regional)." One line of copy, done. ← recommended v1.</li>
<li><strong>(B) Upgrade the base model to HRRR</strong> — <code>models=ncep_hrrr_conus</code> (free, no key, <strong>3 km</strong>, US-only). Distinguishes broad zones (park vs South Bronx) but still blankets dozens of blocks; documented to under-capture UHI.</li>
<li><strong>(C) Static per-neighborhood UHI offset</strong> — add a fixed delta on top of the single forecast (~<strong>+1 to +4 °F</strong> for dense low-albedo areas like the South Bronx/Harlem, near 0 or cooler by water/parks, <strong>largest at night</strong>). Zero extra API calls; derive offsets once from ECOSTRESS/Landsat surface-temp maps or the NYC Heat Vulnerability data.</li>
<li><strong>(D) Live neighborhood truth</strong> — pull a few local sensors: PurpleAir (metered-free API), your own Weather Underground PWS key, or the NYS Mesonet <strong>NYC Micronet</strong> (free, but by data request, not a live REST feed). Satellites (ECOSTRESS 70 m, Landsat) map <em>where</em> the heat is but measure <strong>surface</strong>, not air temp, and only on overpass days.</li>
</ul>
<p>Leanest defensible upgrade: <strong>HRRR base + a static UHI offset table + a one-line disclaimer</strong> that block-level accuracy needs sensors.</p>
<h2 id="phase-4--how-accurate-were-recent-forecasts-no-backend-needed">Phase 4 — "how accurate were recent forecasts?" (no backend needed)</h2>
<p>Use <strong><a href="/rome-wiki/articles/weather/open-meteo-previous-runs-api/" class="wiki-link">Open-Meteo Previous Runs API</a></strong> (<code>previous-runs-api.open-meteo.com/v1/forecast</code>, free/no-key/CORS). It serves each past hour's forecast at a <strong>fixed lead time</strong> (<code>temperature_2m_previous_day1..7</code>, also <code>precipitation</code>, <code>wind_speed_10m</code>, <code>relative_humidity_2m</code>, <code>apparent_temperature</code>). For each past hour <code>h</code>: error = <code>temperature_2m[h] − temperature_2m_previous_dayK[h]</code> → aggregate to MAE/bias per lead K over the last N days (<strong><code>past_days</code> max 93</strong>). <code>temperature_2m</code> for past hours is a best-estimate analysis blend — a fine zero-extra-call truth proxy; swap in ERA5/METAR for a rigorous scorecard. This <strong>removes the only reason Phase 4 wanted a datastore</strong> (below): no self-snapshotting required.</p>
<h2 id="when-youd-need-a-backend-you-still-dont">When you'd need a backend (you still don't)</h2>
<p>Only for: hiding a <em>commercial</em> key, or cache/rate-limit smoothing under real traffic. <del>Scheduled snapshots to score your forecasts</del> — <strong>not needed</strong>: the <a href="/rome-wiki/articles/weather/open-meteo-previous-runs-api/" class="wiki-link">Open-Meteo Previous Runs API</a> already archives past forecasts by lead time, so Phase 4 stays fully client-side.</p>
