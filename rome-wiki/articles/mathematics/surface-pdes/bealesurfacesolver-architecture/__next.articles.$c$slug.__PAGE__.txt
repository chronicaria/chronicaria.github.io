<h2 id="package-spine">Package spine</h2>
<p>The top-level module loads the code in a dependency-aware order:</p>
<ol>
<li><code>src/core/</code> defines vectors, level-set types, cut points, solver options, grid construction, topology, equilibration, metrics, and promoted oblate/tidal figures.</li>
<li><code>src/operators/</code> implements matrix-free and sparse Laplace–Beltrami operators plus surface-mode utilities.</li>
<li><code>src/numerics/</code> provides GMRES and later mimetic, structure-preserving, weak-Hodge, and surface-adjoint machinery.</li>
<li><code>src/pdes/</code> contains diffusion, reaction–diffusion, advection, sphere shallow water, generalized forced shallow water, and quadrature helpers.</li>
<li><code>src/solve_surface_pde.jl</code> ties a <code>SurfaceProblem</code> to a readable high-level workflow.</li>
<li><code>src/verification/</code>, <code>src/cli/</code>, and <code>src/io/</code> keep table reproduction, command-line dispatch, and outputs out of the mathematical core.</li>
</ol>
<p>The central data flow is</p>

<p>This is a useful conceptual boundary: changing the surface belongs at the first stage; changing the PDE should reuse the geometry and topology whenever possible.</p>
<h2 id="public-mathematical-objects">Public mathematical objects</h2>
<p>The package exports concrete level sets such as spheres, ellipsoids, tori, functional level sets, and promoted Roche, Maclaurin, and tidal figures. A <code>SurfaceSolver</code> holds the discretized geometry. Operator calls apply or assemble the Laplace–Beltrami map; high-level problem objects select the equation, geometry, resolution, and time options.</p>
<p>The generalized shallow-water API adds geometry fields derived from <span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML"><semantics><mrow><mi mathvariant="normal">∇</mi><mi>ϕ</mi></mrow><annotation encoding="application/x-tex">\nabla\phi</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.8889em;vertical-align:-0.1944em;"></span><span class="mord">∇</span><span class="mord mathnormal">ϕ</span></span></span></span> and a <code>ForcedSWEParameters</code> object. The structure-preserving and adjoint modules expose more specialized primitives, but those should be read with their own tests and research documentation rather than assumed to be the default solve path.</p>
<h2 id="package-code-versus-research-code">Package code versus research code</h2>
<p>The distinction is load-bearing:</p>
<ul>
<li><code>src/</code> is the promoted reusable package surface.</li>
<li><code>test/</code> and <code>src/verification/</code> are the package-level regression and paper-table checks.</li>
<li><code>research/implementations/</code> contains a large collection of self-contained experimental solvers and demonstrators. Some are mature and heavily verified; many are not yet promoted.</li>
<li><code>research/reference/</code> stores extracted source material, validation harnesses, evidence notes, claims ledgers, and saved results.</li>
<li><code>research/viz/</code> turns data products into figures and movies.</li>
<li><code>research/papers/</code> contains manuscripts and claims ledgers at different stages of preparation.</li>
<li><code>research/phase*</code> and <code>research/brown_dwarf/</code> record plans, result one-pagers, progress, capstones, and caveats.</li>
</ul>
<p>A working script under <code>research/implementations/</code> proves that an idea is executable in its tested setting. It does not automatically make the feature a stable public API. Promotion requires a reusable interface, additive regression tests, and an explicit decision about which assumptions belong in package defaults.</p>
<h2 id="reproducibility-architecture">Reproducibility architecture</h2>
<p>The best result lines use a chain of artifacts: a driver writes data and metadata; a verifier recomputes metrics; a claims ledger records the number and its provenance; a figure builder reads the frozen data; a manuscript cites the ledger. Brown-dwarf work adds golden runs and null controls. This design is more reliable than preserving a conclusion only in prose.</p>
<p>The repository also contains large generated outputs and active working files. A future release should distinguish regenerable artifacts from canonical evidence and attach commit/data hashes to the latter.</p>

<li>How should research-output storage be separated from source control without losing claim provenance?</li>
